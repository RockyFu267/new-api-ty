# DeepSeek 账单后台生成及调用隔离

2026-11-12 新需求：用户接受账单延迟和等待，但不能因为打开、翻查或生成账单卡住 AI 调用。当前代码已在本地实现并验证；**这项报表优化尚未发布到 47.33**。47.33 仍为 12:07 发布的 PG 网关版本。

第二轮代码复核、深翻页修正、冷启动／锁等待／worker 停止的故障测试及本次专用回退约束见 [发布前复核](prepublish-review-20261112.md)。

## 行为变化

旧接口每次读最多 200,001 条原始日志，在网关进程中逐条解析、计算并排序，再截取 50 条；翻页会重复全套工作。新接口只查询独立报表数据库中的每日汇总及最多 51 条明细，不读原始日志、不触发计算任务、不访问计费连接池。

- `cmd/deepseek-report-worker` 是独立进程，不启动 HTTP 网关、渠道调用、订阅刷新或系统任务。
- worker 的源账号只能 SELECT `logs`，不能修改钱包、配额、用户、渠道或价格；另一账号只在独立报表库建表／写表。网关的报表账号只有报表库 SELECT 权限。
- 源和目标各一个连接；默认每批 200 条原始日志，批次结束后休息 2 秒。源查询按主键范围读取，不在源库执行全历史聚合。
- 正常尾部导入会回看最近 200 条，定期小批量复核已扫描范围，补捉提交顺序和 ID 顺序不一致的日志。忙时每十批至少留一批复核，闲时复核不挤占新日志。
- 明细、每日汇总、导入位置在报表库同一事务提交；重跑、故障恢复和多个 worker 竞争不会重复累计。SQLite 清理后复用行 ID 时，以“日志 ID＋请求 ID”区分记录。
- 网关报表池最多 2 个连接、查询最多同时 2 个、单次读取上下文 2 秒。源库、报表库禁止配置为同一库。PG 报表库在网关启动时离线也不会阻塞网关启动，恢复后连接可自行重连。
- 默认仍查看最近 30 天，支持最长 90 天筛选。汇总由每日数据生成；明细按时间、日志 ID、稳定键进行游标分页，取消全量排序、OFFSET 和 20 万条限制。
- 普通用户的汇总与明细都限定自己；管理员保留全员汇总、人员选择。切换筛选条件会清除分页游标。
- 历史补算未完成时显示进度及更新时间，不把部分历史当成完整零费用账单。worker 停止后显示最后生成的结果及暂停提示。刷新只读取结果，不要求后台立即重算。
- 网关无报表配置时显示未配置，不降级回扫描原始日志。报表库故障只让账单接口返回友好的 503，不把数据库连接细节传给普通用户；AI 计费仍走原有逻辑。
- 未导入报表的 DS 日志会阻止该批日志清理；PG 的日志清理同时改为先选一小批 ID 再删除，避免 PostgreSQL 忽略 DELETE LIMIT 而误删整个日期范围。

实时扣费、部门配额、钱包、普通模型定价、DS 定价版本和汇率没有改变。报表读取已保存的实际计价快照；旧历史仍沿用原来的参考价格模拟，绝不再次扣费。报表仅改变展示计算与数据读取路径。

## 数据与时间含义

报表库新增 `deep_seek_bill_facts`、`deep_seek_bill_dailies`、`deep_seek_bill_states`，不在主库新增这些表。跨午夜记录按原请求开始时间及实际快照归日，与原账单规则一致。没有使用“次数×平均价格”估算代替实际逐笔金额。

首次运行会补已有日志。20 万条按默认上限理想下约 34 分钟，再加网络、限额及数据库执行时间；用户可继续调用 AI，页面稍后查看。记录 ID 中有空号，界面进度只是近似位置进度。新记录也可能延迟，复核可能继续修正暂未出现的记录；“后台最后检查时间”不是审计最终封账时间。worker 断开会暂停，不存在为了追实时而无限紧循环、增大连接池或在页面请求内追赶历史的逻辑。

事实和每日汇总独立于原日志清理保留。**原始日志还在时可以重建报表；清理原日志后必须备份报表库，不能把它当作可随意丢弃的缓存。** 原始日志若已被清理，再修改旧历史参考模拟规则，需要另行设计版本化重算，不能默默改写实际扣费或已封存金额。

## 本地验证

真实生产副本已脱敏，另加本机模拟数据，所有压力调用走 127.0.0.1 模拟上游，未消耗 Ucloud 额度。PG 容器限制 4 CPU／4GiB；网关和负载程序在 Windows 宿主机，不能把结果当成整套服务仅用 4 CPU 的容量承诺。

1. 同一 187,385 笔 DS 账单，旧查询 9.552 秒，新缓存查询首次实测 0.0196 秒，金额和原用户 #194 的 176,892 笔历史统计一致。
2. 补至 211,885 笔后，查询 0.0184 秒，仍只返回 50 条，正常跨过原 20 万条限制。
3. 100 名模拟用户、64 并发下，基线 1,000 次 AI 调用全部 200；连续查询／翻页 105 次时，另外 1,000 次 AI 调用全部 200；账单查询 P95 约 53ms、P99 约 65ms。
4. 实际禁用本地报表库连接并终止其连接，143 次报表查询失败且只返回通用错误；同期 500 次 AI 请求全部 200，用户、Key、渠道、配额账单、消费日志及 Token 分析全部对账一致。重新开放报表库后，不重启网关即可恢复查账。
5. 从一个空报表库开始，默认限速 worker 实际生成历史记录，同时 4,000 次 AI 调用全部 200，P99 约 305ms，所有金额和统计检查一致。
6. Linux 非特权用户、只读文件系统、0.25 CPU、256MiB、32 tasks 限额下 worker 持续运行，样本 RSS 约 12.77MiB、6 tasks；没有日志错误，SIGTERM 正常结束。
7. Go 回归覆盖：源日志库不可用仍可读历史、后台中断整批回滚、复核补迟到记录不重计、跨月／跨午夜、用户权限、游标同秒排序、ID 复用、日志清理保护、报表库启动时离线、错误不泄露连接信息。
8. 前端 4 个文件共 8 项相关测试、typecheck、lint 和生产构建通过；根模块全量 Go 测试及 Linux 构建通过。

前后两轮测试的冷热缓存不同：第一轮 AI P99 基线／并行报表／报表离线约 323／313／330ms；复测约 1569／324／342ms。不能据此宣称报表会让 AI 变快；明确验证的是调用全部完成、对账一致，且报表故障未把失败传给 AI 调用。

压测、审计和合并后的脱敏结果见 `async-validation-20261112.json`；含凭据的原始环境和完整输出保留在项目父目录 `.deployment/pg-rehearsal_20261112_105055/`，不提交 Git。

## 发布前配置

本次没有对 47.33 新建报表库或安装 worker。发布要同时更新前端、网关、独立 worker 和配置；不能只替换后端，让旧前端把“未生成”误显示成零费用。

需准备不同于主库的 `new_api_ty_reports`，以及三个独立数据库角色：

- `new_api_bill_source`：主库 CONNECT、public USAGE、logs SELECT，仅此；无写入和建库权限。
- `new_api_bill_writer`：拥有报表库，public USAGE/CREATE；无主库写入权限。
- `new_api_bill_reader`：报表库 CONNECT、public USAGE、报表表 SELECT；无建表和写入权限。通过 writer 的 `ALTER DEFAULT PRIVILEGES ... GRANT SELECT ON TABLES` 覆盖后续建表。

建议撤销报表库 public 的 CONNECT 和 schema CREATE，分别显式授予；PostgreSQL 旧版本尤其不能依赖 public 默认权限。真实随机密码放受限配置文件，不写到源码和部署清单中。

worker 配置模板在 `scripts/deepseek-report-worker.env.example`。网关 `.env` 新增 `DEEPSEEK_REPORT_DSN`，使用 reader；其 options 应包含 connect_timeout=2、lock_timeout=250、statement_timeout=1500、default_transaction_read_only=on。writer 不设置只读。不要给报表连接沿用主网关 32 连接的池或原主库管理员权限。

`scripts/deepseek-report-worker.service` 使用 DynamicUser、独立挂载的可执行文件、GOMAXPROCS=1、GOMEMLIMIT=160MiB、CPUQuota=25%、MemoryMax=256M、低 CPU/IO 优先级和只读系统。只将 worker 二进制安装为 0755，主网关二进制和含凭据文件不放宽权限；systemd 读取 root:root 0600 的 `report-worker.env` 后传递给 worker。不要直接复用网关启动入口或启用业务后台任务。

操作顺序：新库及角色 → 构建／启动限速 worker → 检查独立报表及进度 → 配置并发布新网关和前端 → 再验证真实调用。报表服务可以单独 `systemctl stop deepseek-report-worker` 暂停，不需要停止 AI 网关。升级和停止 worker 也不会要求账单页面等待退出。

模型代码使用 GORM，支持 SQLite/MySQL/PostgreSQL；SQLite 的源和报表必须是不同文件，建议报表文件启用 WAL。ClickHouse 日志源的 ID／清理模式不同，本 worker 未声明支持。

## 隔离边界

两套数据库若共享同一 PG 实例和磁盘，仍会共享底层硬件；不能承诺资源耗尽时数学意义的零影响。本方案消除了账单查询对 AI 的同步任务／连接池依赖，并限制后台工作量，故障时先让报表不可用。规模进一步上升，可把报表库迁到另一实例，源改为只读副本，不改实时计费算法。仍须监控磁盘、连接等待、worker 延迟和备份，不能靠无限提高 worker 速度追账。
