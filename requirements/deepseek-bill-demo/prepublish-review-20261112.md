# 账单后台优化的第二轮发布前审查

状态：2026-11-12 本地复核完成，**未发布到 47.33**。本轮没有修改生产服务器。

后续状态：2026-11-13 用户明确授权发布，已上线，见 [生产发布记录](production-rollout-20261113.md)。以下保留 11 月 12 日的审查结论和当时的部署状态。

## 代码与发布范围

以 12:07 已发布 PG 版本的源文件清单、SHA-256 及 Git 基线为参照核对差异。`service/billing_session.go`、`service/quota.go`、`service/text_quota.go`、`model/department_quota.go`、`model/quota_reserve.go`、用户／Key／渠道更新和 DS 定价规则文件没有本轮新增变更。不要把这些文件相对旧 Git 提交的差异误认为本轮修改。

新报表仅在主程序启动时创建自己的延迟连接池，失败只记日志；AI 转发和实时计费不调用报表读取或后台计算。主库迁移列表不包含新报表表；只有独立 worker 对目标报表库建表。共享锁辅助方法改为判断实际事务的数据库类型，SQLite 跳过行锁、PostgreSQL/MySQL 使用行锁，防止独立 worker 尚未初始化全局主库类型而漏锁；相关测试及原有配额测试通过。

原始日志清理新增导入保护：报表尚未保存的 DS 记录不删。此检查不处于 AI 转发事务中，报表不可用时暂停清理而非删除历史。新报表库必须纳入备份，不能在清理源日志后随意删除。

## 本轮发现及修正

深翻页原先将复合游标展开成 OR 条件。实际 PG 查询计划显示，可能回扫大量比游标更新的记录：定位到约第 100,000 条时，明细 SQL 为 311.354ms、命中 24,491 个块；改为复合行比较后为 0.299ms、24 个块。这是本地冷热缓存混合样本，不是生产容量承诺。SQLite/MySQL/PostgreSQL 均支持该行比较；额外的时间上界便于 MySQL 使用范围索引。

新增分页边界用例：两条历史保留记录可以时间相同、日志 ID 相同，但请求 ID 不同；它们恰好落在两页边界时，仍各出现一次。实际 PG HTTP 查询验证约第 50、100,000、180,000 条之后的页面均成功，50 条明细，整次接口约 10–11ms。

## 最终构建的故障测试

下述调用均在本地脱敏副本及模拟上游上进行，不调用付费渠道。每组 100 名模拟用户、64 并发，混合 DS 和普通模型、流式和非流式请求。

| 故障条件 | AI 调用结果 | 账单表现 | AI P99 |
| --- | --- | --- | --- |
| 关闭报表库连接后冷启动网关 | 500/500 成功 | 网关约 2.832 秒健康；报表库恢复后无需重启网关即可查账 | 352.58ms |
| 对报表明细表持有排他锁 | 500/500 成功 | 12 次报表查询均友好返回 503，解锁后恢复 | 330.77ms |
| 停止后台 worker | 500/500 成功 | 35 次查询仍返回已保存账单；恢复 worker 后继续导入 | 319.15ms |

每组检查用户请求数、部门账单、消费日志、用户／Key／渠道扣费一致、钱包未误扣、无新增悬挂预扣、输入输出 Token 与缓存量、用量队列清空。历史用户 #194 的汇总保持一致。worker 停止提示使用 90 秒心跳阈值，本轮短时停机测试验证的是历史可读，没有等待提示状态过期。

根模块全量 `go test -count=1 ./...`、前端 4 文件 8 项相关测试、typecheck，以及最终 Linux/amd64 网关构建通过。前端源码本轮未修改，之前生产构建已通过；本轮 Go 构建使用现有完整前端产物。

## 发布与回退约束

1. 保持现有 PG 主库及业务角色；新增报表库、只读源角色、独立 writer、只读 reader。先启动受限 worker，验证角色权限、导入进度与历史金额，再切换网关。worker 没准备好时可以等待，不能临时让页面恢复扫描原始日志。
2. 在当次 `update_时间` 目录备份当前运行的网关二进制、前端产物／内嵌版本、启动配置及文件哈希；记录新旧进程和健康检查结果。不要只留 Git 的旧提交，因为当前线上 PG 修复尚有未提交文件。
3. 出现异常先停止报表 worker，观察 AI 调用；若需撤销本次网关更新，恢复本次发布前备份的 PG 网关二进制及配置，继续使用现有 PG 数据。**不恢复旧数据库、不切回 SQLite、不覆盖上线期间产生的账单和用户配置。** 旧 PG 网关会忽略新的报表表；恢复后避免重复打开旧的同步账单页。
4. 本轮没有执行生产发布或生产回滚，也没有声称测试过尚未创建的生产更新目录。既有“PG 迁回 SQLite”脚本属于上次迁库预案，不能拿来回退这次报表优化。

故障隔离不等于无限容量保证。同一 PG 实例仍共享 CPU、缓存和磁盘，worker 的 CPU 配额也不会限制 PostgreSQL 服务进程自身的 CPU；源查询靠小批量、独立连接、只读权限、超时与批间暂停约束。继续维持当前低速设置，不能为了追账任意提速。
