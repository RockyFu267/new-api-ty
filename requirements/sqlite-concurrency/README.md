# SQLite 配额并发修复

确认时间：2026-11-06。

## 现场问题

- 47.33 使用 SQLite，现场日志模式为 `delete`，未配置 SQL 连接池大小，原默认最大连接数为 1000。
- 并发调用在 `ReserveDepartmentQuota` 读取用量后插入预占记录时产生 `SQLITE_BUSY`，请求在转发前返回 500。
- 同类冲突还发生在配额结算和 Token 汇总。已确认一笔成功请求的配额记录停留于 `reserved`，实际消耗日志存在。
- 优刻得的组织级 60 RPM 上游限流是另一项独立问题，本批不修改上游或网关限流。

## 实现

- 使用当前 glebarez/go-sqlite 驱动支持的 `_txlock=immediate`：事务在读取配额前获取 SQLite 写锁，再执行检查与写入，避免并发读后升级写锁冲突。
- 默认通过每连接 `_pragma` 设置 WAL 和 1000ms busy timeout。已有显式 `_pragma` 保留；旧 `_busy_timeout` 并不被该驱动用来设置连接等待时间，不能仅依赖旧参数。
- SQLite 主库及独立日志库默认最大空闲/打开连接数改为 4；显式 SQL 连接池环境变量继续生效。MySQL/PostgreSQL/ClickHouse 默认连接池参数不变。
- 部门配额预扣、调整预占、结算/退款及用量汇总只在 SQLite 的 BUSY/LOCKED 错误下重试完整事务，最多 6 次，间隔递增；失败事务先回滚，不能只重放基于旧快照的写语句。
- 业务错误（额度不足等）不重试；其他数据库继续原有事务与行锁行为。原日/周/月上限、长任务结算、钱包兜底和价格算法不变。
- 不新增数据库表或字段。WAL 会产生 SQLite 的 `-wal`/`-shm` 辅助文件，备份继续使用 SQLite backup API 或停服后的完整备份。

## 范围与遗留数据

- 本批修复锁竞争和瞬态写入失败，不是无限重试或断电恢复机制。锁长期不可用时仍返回错误并保留已有审计信息。
- 不按时间自动清空 `reserved`：长任务可能仍在运行，直接释放会破坏配额核算。
- 现场已挂起的历史记录不随本地代码修改自动变化，需要部署后根据请求 ID、实际消费日志和 API Key 额度一起对账处理，避免只修部门账而遗漏令牌差额。
- 当前仅完成代码及本地验证，尚未提交或部署，也未修改服务器数据。

## 验证

- 使用真实文件数据库和多连接：跨日/周但同月的历史消耗保持生效；并发请求只有一个能占用剩余月度额度。
- 并发重复结算、并发重复退款不会重复记账或遗留预占，钱包金额不变。
- 独立连接持有写事务时，WAL 读者仍可读取已提交数据。
- 使用真实驱动锁错误注入事务回滚：完整重试只生成一条配额记录；业务错误只执行一次。
