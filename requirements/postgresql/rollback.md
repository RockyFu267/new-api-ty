# 允许丢弃试运行计费的快速回滚

发布更新：2026-11-12 已完成 47.33 生产切换，脚本和恢复点已保存在 `/data/app/new-api-ty/update_20261112_120307/`。以下“本次没有上传”等描述指发布前本地演练阶段，最新结果以 [生产切换记录](production-cutover-20261112.md) 为准。

2026-11-12，用户明确接受“切换 + 实际使用期间发现失败 + 回滚过程中”的计费丢失。此授权仅覆盖该试运行窗口，不覆盖切换前历史，也不代表允许丢弃渠道、密钥、用户归属或部门权限变更。

## 策略

采用切换前停机、账务已经结算完成时的恢复点：旧程序、旧 `.env`、完整 SQLite 在线备份及 SHA256。发现失败后停止 PG 版服务，恢复这三个文件并启动旧 SQLite 版，不等待 PG 可用，不把试运行账务反向导回 SQLite。PG 原数据保留供排查，不删除数据库或 PostgreSQL 服务。

恢复后，余额、配额已用量、使用日志、Token 分析、充值等数据库状态回到恢复点；该窗口产生的计费及充值调整不补记。API 调用恢复后仍要重新计费，供应商已经收取的费用不会因为网关回滚而退回。切换前已经持久化的历史不丢。源代码 checkout 不执行破坏性 reset：运行旧可执行程序即可恢复其内嵌前端，此脚本只适用于本次前端未变的后端／数据库迁移。

验证窗口应冻结渠道、模型价格、部门权限、用户维护等非计费改动；新用户首次登录也可能创建用户记录，宜先使用已有用户验证。如果实际发生这些变更，需单独记录并补回，不能仅因用户接受计费丢失而直接丢弃。脚本不会自动识别 PG 中这类新增配置，执行回滚前必须确认配置冻结有效。

## 已提供脚本

- `scripts/sqlite_cutover_rollback.py`：创建恢复点，以及停止状态下校验并恢复。非空备份目录不覆盖；运行中的进程／开放端口、错误路径、损坏备份、不匹配服务、Redis 或分离日志库配置均拒绝。恢复时把当前程序、配置、SQLite 及旧 WAL/SHM/journal 保存在 `failed-state-*`；不把旧 WAL 留在恢复后的 SQLite 旁边。
- `scripts/rollback_to_sqlite.sh`：调用已有 `stop.sh`，执行恢复，再调用已有 `start.sh`，检查本地健康状态。显式清除继承的 PG DSN 并指定恢复后的 SQLite 路径，避免终端导出的环境变量覆盖 `.env`。
- `scripts/test_sqlite_cutover_rollback.py`：Windows 和 Linux 都通过的恢复、坏备份拒绝、进程与端口保护测试。

正式更新时将两份运行脚本一并放入 `/data/app/new-api-ty/update_时间/rollback-tools/`，保留原有根目录 start/stop 脚本。先排空请求并停止旧网关，再执行一次：

```bash
python3 /data/app/new-api-ty/update_时间/rollback-tools/sqlite_cutover_rollback.py checkpoint \
  --service-root /data/app/new-api-ty \
  --update-dir /data/app/new-api-ty/update_时间
```

`update_时间` 是占位符，实际目录必须为 `update_YYYYMMDD_HHMMSS`，不能覆盖以前恢复点。先校验 `sqlite-rollback/manifest.json` 已生成，再迁移到 PG。需要回滚时的一条入口命令：

```bash
bash /data/app/new-api-ty/update_时间/rollback-tools/rollback_to_sqlite.sh \
  /data/app/new-api-ty /data/app/new-api-ty/update_时间
```

本次没有上传或执行这些生产命令，47.33 网关没有变更。正式切换必须先生成该次最终恢复点，不能使用本地演练数据库替代生产数据。备份含密钥和用户数据，目录仅允许管理员访问，不提交 Git。

## 实际演练结果

本机另开独立 53020 端口，以最近生产提交的旧版程序和脱敏生产 SQLite 运行，产生 1 次消费后停止并建立恢复点。将该快照迁入专用本机 PG，换为新版程序并成功增加 3 次消费，再执行恢复旧程序／旧配置／旧 SQLite，健康检查通过后再实际调用 1 次。

- 回滚后的 SQLite 消费从恢复点的 1 次变为验证后的 2 次，丢弃 PG 试运行的 3 次消费，符合授权边界。
- PG 保持 4 次消费，证明回滚没有清库，也没有把恢复后的新请求继续写入 PG。
- 旧二进制、配置及恢复前数据库哈希校验通过；恢复后的钱包、API Key、配额账单及消费日志对账一致。
- 损坏备份被拒绝且当前文件不变；服务仍运行时拒绝替换文件。
- 从停止试运行服务到旧服务恢复健康，本机实测 **4.49 秒**。这是 Windows 本地这次恢复的测量，不是 47.33 的时间保证，不包含等待人为发现故障和排空长请求。生产通常以分钟级恢复为目标，仍要以正式环境条件为准。
- Linux 隔离容器内，恢复／坏备份拒绝／真实进程及端口保护 3 项测试通过，Bash 入口语法检查通过。完整应用来回切换在本机 Windows 完成；尚未在 47.33 执行。
