## 本次实现

1. `cmd/migrate-sqlite-postgres`：从只读、已关闭的 SQLite 在线备份迁入明确确认的空 PostgreSQL 数据库。使用当前应用 GORM 模型建表，保留两张旧知识库表、源索引和唯一约束，保留序列高水位；逐表计数和内容校验通过后才提交批量数据。
2. 错误保护：目标非空、数据库名确认不符、非 public 默认 schema、其他应用 schema、并发迁移、未知源表／字段、不支持的索引表达式／排序规则／触发器／外键、无效布尔值、非空源 WAL、源文件改变，均拒绝继续。不删除或清空目标数据。失败时批量数据回滚，已创建的空表结构可能保留，序列也可能有空号。
3. `model/database_retry.go`：只重试数据库明确拒绝或回滚的写入，例如 SQLite BUSY/LOCKED、PostgreSQL 死锁／序列化失败／锁等待超时、MySQL 死锁／锁等待超时。覆盖 API Key、钱包原子预扣及回补、用户与渠道计数、日志、用量事件。不会盲目重放断网、EOF 或未知提交结果。
4. 预扣失败分类：真实余额不足保留 403；数据库锁竞争耗尽重试后返回 503，内部数据库错误返回 500。数据库失败不会触发钱包兜底或切换上游重试。
5. `DepartmentQuotaCounter`：新增按用户、周期类型、周期起点保存的派生汇总表。第一次使用从原账单初始化，之后预扣、调整、结算、退款与账单在同一个事务中更新。统一用户行锁后再锁账单，用户之间不共用全局写锁。日／周／月限制仍同时生效，周日零点刷新周额度；调部门不清空已用额度，跨期请求仍计入开始时所属周期。实际结算允许原有的单任务超额，但后续请求会被限制。用户软删除后，已发出的请求仍可结算。
6. 用量分析按批次合并相同维度，批量删除队列，批次与检查点原子提交；有积压时连续消费，不再每处理 500 条固定等待 5 秒。
7. PostgreSQL 默认连接池从原通用的 100/1000 调整为闲置 16／打开 32，仍允许环境变量覆盖；SQLite 和 MySQL 默认值不变。测试使用同步写入、无 Redis、无进程内批量延迟记账。

原有模型计价公式、DeepSeek 价格版本及快照、7.3 汇率、部门优先／钱包兜底语义保持不变。新增计数是账单的派生结果，不是新的收费来源或独立 DeepSeek 配额。

## 测试条件与结果

本机 Docker PostgreSQL 17.11，限制 4 CPU、4 GiB 内存；`shared_buffers=256MB`、`max_connections=100`，应用池 32/16，`SQL_MAX_LIFETIME=300`。网关、Python 模拟上游和 HTTP 压测程序在 Windows 宿主机运行，不是全套服务仅占 4 CPU／4 GiB。所有压测调用本机模拟上游，未花费供应商额度。

生产历史数据之外，增加 100 名模拟用户、200 个 API Key、2,192,000 条历史配额账单，其中 4 名用户各至少 500,000 条。模拟返回每次输入 100,000、输出 1,000、缓存命中 98,000 tokens；这些是用于精确对账的受控返回值，不代表真实模型生成能力。

| 场景 | 请求／并发 | 结果 | 请求/秒 | P95 / P99 |
| --- | --- | --- | --- | --- |
| 优化前，4 名重度用户各 50 万历史账单 | 1,200 / 64 | 全部 200，账务一致 | 17.39 | 5.879s / 6.797s |
| 优化后，同一大历史场景，服务就绪后发起 | 1,200 / 64 | 全部 200，账务一致 | 191.30 | 0.533s / 0.610s |
| 优化后，100 用户、两类 Key、普通及 DS 模型、混合流式 | 10,000 / 256 | 全部 200，账务一致 | 140.04 | 5.877s / 8.965s |
| 真实发送 512 KiB 提示词，100 用户，全部流式，上游模拟等待 1s | 256 / 64 | 全部 200，账务一致 | 50.62 | 1.462s / 1.508s |

10,000 次测试中，输入合计 10 亿、输出 1,000 万、缓存命中 9.8 亿 tokens；用户、API Key、渠道、已结算配额账单与消费日志增加的金额全部为 9,430,000 quota。钱包不变，预扣全部关闭，用量事件队列排空。不是只检查 HTTP 成功数。

单独故障及边界验证：

- 月额度耗尽时后续请求为 403，未调用上游、未多扣 Token；加钱包后只扣钱包，部门额度不再增加。
- 上游 503 后配额及 API Key 预扣退回，消费日志不计成功消费。
- 分别持续锁住 Token 行和用户行，HTTP 在约 6.36／6.37 秒返回 503；未调用上游、没有部分扣费。解除锁后下一次请求成功，扣费一次。
- 未分配部门、部门未配置模型权限，即使有钱包也不能调用模型。
- 独立 Python Decimal 重算 10,073 条模拟 DS 消费，金额与日志、快照一致；逐一核对 312 个派生周期计数与原始账单一致。以上计数取故障演练结束时，后续长上下文测试又增加 256 次请求。
- 真实 PostgreSQL 多连接测试覆盖 32 个 agent 抢同一月余额、16 次重复结算、真实锁超时后重试、持久锁失败无多扣。
- 自动测试覆盖每日／周刷新不能绕过月上限、跨月完整周、调部门、跨月结算、退款幂等、写入失败整笔回滚、旧预扣迁入后初始化计数、用量队列跨批次及失败重试。
- 对原用户 #194 的 176,892 条历史 DS 消费，独立读取原 SQLite 计算并核对本地 API 的输入、输出、缓存、峰谷金额、实际扣款；日／周／月用量、钱包、Token 分析接口也完成核对，汇率仍是 7.3。
- 迁移集成测试验证无效数据导致前面已复制的表一起回滚、大整数不经浮点舍入、中文／JSON／布尔／时间戳、唯一索引、删除后的序列高水位、归档表默认值、重复迁入非空库被拒绝。

一次紧接重启就发起的开发测试出现 64 次连接未就绪；没有扣费。压测程序已增加明确的 `/api/status` 就绪检查，表中采用就绪后重新执行的完整结果，未通过重试隐藏请求错误。

根模块 `go test ./...`（包括两组本机 PG 集成测试）全部通过；Linux amd64、CGO 关闭的全模块构建通过。全量测试还修复了两个测试夹具：模型列表认证测试补齐部门授权数据；原始 HTTP/2 测试服务器使用 TCP 半关闭并排空输入，避免 Windows 立即关闭连接发送 TCP reset，掩盖原本测试的 GOAWAY/RST_STREAM。未修改这两处的生产协议行为。

详细脱敏数字见 [local-validation-20261112.json](local-validation-20261112.json)。完整负载脚本、原始输出、逐表迁移报告和只读生产核验记录保留在父目录 `.deployment/`，其中有测试凭据的文件不进入 Git。

## 可重复执行的代码验证

根模块：

```powershell
# 两个地址均必须指向本机专门的空测试数据库；不要使用生产连接。
# LOCAL_POSTGRES_TEST_DSN 的数据库名必须以 _test 结尾。
# LOCAL_MIGRATION_TEST_DSN 必须以 _migration_test 结尾，public 初始无表。
$env:LOCAL_POSTGRES_TEST_DSN = '<本机测试库 DSN>'
$env:LOCAL_MIGRATION_TEST_DSN = '<本机空迁移测试库 DSN>'

go build -o migrate-sqlite-postgres.exe ./cmd/migrate-sqlite-postgres
$env:MIGRATION_POSTGRES_DSN = '<本机空迁移验证库 DSN>'
.\migrate-sqlite-postgres.exe -source '<已关闭的 SQLite 备份>' -confirm-database '<目标库名>' -report migration-report.json
```

## 后续生产切换边界

本次完成的是本地演练，不是生产切换。最后只读核验 47.33 网关 PID 仍为 94510，进程未设置 SQL_DSN，53000 健康检查成功。

以后发布应按原约定创建 `update_时间/`，另行执行：停止接收请求并等待在途请求结束，保留原程序／配置／SQLite 在线备份，再将最终快照迁入空 PG 并完成对账，最后才修改生产 SQL_DSN 和启动。统一主库和日志库已验证；如果将来单独设置 LOG_SQL_DSN，需要另行迁移对应日志库，当前 CLI 不会自动合并多个源。

建议保持当前无 Redis、无内存延迟批量记账的生产模式，使用 32/16 连接池和 `SQL_MAX_LIFETIME=300`；DSN 可以显式配置 `lock_timeout=1000&statement_timeout=30000`。故障测试采用该 1 秒锁等待上限与最多 6 次安全重试，不能只调大连接数。生产参数仍需结合 47.33 上其他服务的实际资源使用确定。

必须一次停机切换，不能让旧版和新版同时向同一个 PG 写配额账单：旧版不了解派生计数，会使新版读取过时计数。用户随后明确接受切换、实际使用试运行和回滚期间的计费丢失，因此采用切换前 SQLite 快照回滚，不反向迁移试运行账务。详见 [允许丢弃试运行计费的快速回滚](rollback.md)，已补充脚本与本地实际演练。若在同一个 PG 上回退过旧版本，重新升级前仍要离线从账单重建派生计数。

周期账单是计数重建的来源，不能直接清除；常规消费日志仍遵守现有清理和 Token 分析历史导入保护。当前日志、用户／渠道统计继续沿用原有独立写入方式，本次没有增加跨库或网络故障下的分布式 exactly-once 保证。SQLite 锁错误被修复和迁入 PG，并不意味着无限并发或永不失败；256 并发测试的 P99 约 9 秒就是本机接近压力上限时的实际延迟，应结合连接等待、锁等待、错误率、磁盘和队列积压监控容量。
