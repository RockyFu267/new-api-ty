# Chat 功能改造需求

## 背景

当前系统同时存在“聊天”和“游乐场”两个入口，但现有“聊天”主要用于打开预设的外部聊天页面或外部客户端，不符合 TIANYAN 内部 Demo 对原生模型聊天功能的需求。

为避免概念混淆，本文将当前已有的“聊天”称为“原始聊天”，将当前已有的“游乐场”称为“原始 Chat 功能参考”，并将后续新增的原生聊天功能称为“Chat”。

## 需求范围

### 1. 屏蔽原始聊天

- 隐藏侧边栏中当前已有的“聊天”入口。
- 用户不再通过 UI 进入聊天预设、外部网页 iframe 或外部客户端跳转功能。
- 如果确认不存在其他功能依赖，可以进一步删除原始聊天的前端路由和相关代码；第一阶段至少保证入口不可见。
- 当前原始聊天相关能力包括聊天预设、外部链接模板、API Key 注入、iframe 页面和外部协议唤起。

### 2. 保留游乐场作为参考

- 当前游乐场功能暂不改造，保留现有实现和行为。
- 将侧边栏入口名称从“游乐场”改为“原始 Chat 功能参考”。
- 保留其页面、路由、流式对话、消息展示、参数设置和本地会话存储能力，供新增 Chat 功能开发时参考。
- 该入口仅用于参考和对照，不作为最终的新 Chat 产品入口。
- 已知问题：界面虽然允许切换渠道模型，但实际请求没有按用户选择切换到对应渠道，最终仍只使用同一种模型响应。
- 已知问题复现场景：平台同时添加了本地离线部署的 Qwen 渠道和 AWS Bedrock 渠道；用户在界面选择不同渠道模型后，实际聊天仍表现为使用同一种模型。
- 在原因尚未完成定位前，不能复用原始 Chat 功能参考中的渠道模型选择和请求路由逻辑作为新 Chat 的正确实现。

### 3. 新增 Chat 入口与功能

- 在侧边栏新增独立的“Chat”入口。
- Chat 页面展示当前用户可使用的渠道模型列表。
- 用户选择某个渠道模型后进入对应聊天界面。
- 聊天请求必须使用用户选择的渠道和模型，不能在未提示用户的情况下切换到其他渠道模型。
- 渠道选择必须参与后端实际路由，不能只在前端保存或展示；后端应能够验证请求最终命中的渠道与用户选择一致。
- 即使不同渠道配置了相同或相近的模型名称，也必须保留明确的渠道身份，避免按模型名称重新分发到其他渠道。
- 新 Chat 的设计和测试至少要覆盖本地离线 Qwen 与 AWS Bedrock 两个不同渠道之间的真实切换。
- 新 Chat 应为系统内置页面，不依赖原始聊天的外部网页 iframe 或外部客户端。
- 可参考游乐场的流式输出、消息渲染、输入框、参数控制和错误处理，但不直接改造或破坏游乐场。

## 初步用户流程

1. 用户点击侧边栏中的“Chat”。
2. 系统加载该用户有权使用的渠道及其模型。
3. 页面按渠道展示模型，或提供渠道与模型的组合列表。
4. 用户点击目标渠道模型。
5. 系统进入聊天页面，并明确展示当前渠道和模型。
6. 用户发送消息，系统通过所选渠道模型进行流式回复。
7. 用户可返回列表选择其他渠道模型开启新的聊天。

## 验收标准

- 侧边栏不再显示原始聊天入口。
- 原“游乐场”入口显示为“原始 Chat 功能参考”，其现有功能可正常使用。
- 侧边栏显示新的“Chat”入口。
- Chat 页面能够显示当前用户有权使用的渠道模型。
- 用户能够选择指定渠道模型并完成正常聊天。
- 页面能够明确显示当前正在使用的渠道和模型。
- 用户在本地离线 Qwen 与 AWS Bedrock 之间切换时，后端实际命中的渠道和模型必须随选择变化。
- 测试与日志必须能够证明最终命中的渠道 ID、渠道类型和模型，而不能仅断言前端下拉框选项发生变化。
- 不具备权限或不可用的渠道模型不能被用户正常发起聊天。
- 新 Chat 不依赖外部 iframe 或外部聊天客户端。

## 非本阶段目标

- 不改造现有游乐场的内部实现。
- 不在需求确认阶段直接删除后端通用模型中继能力。
- 暂不定义聊天记录的服务端持久化、会话共享、附件、联网搜索和知识库功能。

## 待确认事项

- “用户已经添加的渠道”具体指用户本人创建的渠道，还是管理员创建且当前用户有权限使用的渠道。
- 同一模型存在于多个渠道时，是分别展示每个“渠道 + 模型”组合，还是合并模型后由系统自动选渠道。
- 新 Chat 的聊天记录仅保存在浏览器，还是需要保存到服务端数据库。
- 是否允许普通用户看到渠道名称、渠道 ID、上游地址等运维信息。
- 第一阶段是否只支持文本和流式回复，还是同时支持图片、文件、工具调用及推理内容。
- 原始聊天代码是仅隐藏入口，还是在新 Chat 稳定后彻底删除。

## 第一阶段实现状态

截至 2026-09-01，第一阶段可运行版本已完成：

- 已从侧边栏隐藏原始聊天预设入口，原路由代码暂时保留，避免在验证新 Chat 前执行不可逆删除。
- 已将“游乐场”入口显示名称改为“原始 Chat 功能参考”，原有游乐场行为不变。
- 新 Chat 验收满意后，已关闭“原始 Chat 功能参考”的侧边栏入口；游乐场路由和源码继续保留，仅供内部开发参考。
- 已新增 `/chat` 页面，按“渠道 + 模型 + 分组”展示当前用户可用的组合。
- 已新增用户渠道模型只读接口，仅返回渠道 ID、渠道名称、渠道类型、分组和模型，不返回密钥或上游地址。
- 新 Chat 请求会携带 `channel_id`；后端在分发前验证用户分组权限、渠道状态及渠道模型能力，并锁定指定渠道。
- 后端响应附带实际锁定的渠道 ID、渠道类型和模型响应头，便于 Demo 调试和日志核验。
- 新 Chat 复用了游乐场的消息展示、流式响应、输入和参数组件，但使用独立的页面状态，不读取或覆盖游乐场的本地聊天记录。

第一阶段暂未实现服务端聊天记录持久化、附件、联网搜索、知识库以及渠道类型名称美化。

### 2026-09-02：渠道模型聊天提示管理

#### 背景

用户选择“渠道 + 模型”进入新 Chat 后，当前空白会话页仍展示游乐场默认文案“开始一场游乐场对话 / 使用入门提示词测试模型，或在下方编写自己的请求”。该文案既不符合新 Chat 的产品语义，也不能表达不同渠道模型的费用和使用边界。

渠道模型的成本与用途并不相同：本地部署模型可能免费开放使用，AWS Bedrock 等上游模型可能按量产生费用。管理员需要在用户开始对话前展示有针对性的说明，避免用户在不了解成本的情况下随意调用付费模型。

#### 管理入口

- 在“系统设置 → 运维 → 渠道维护 → 聊天提示管理”增加管理入口。
- 管理页面展示系统当前已经接入且可识别的“渠道 + 模型”组合。
- 管理员可以为每个渠道模型组合分别编辑进入聊天页时展示的标题和说明内容。
- 该能力属于管理员运维配置，普通用户只能查看最终生效的提示内容，不能修改。

#### 展示规则

- 用户选择渠道模型进入 Chat 后，在尚未发送第一条消息时展示该组合对应的管理员提示。
- 配置内容替换当前游乐场默认标题和说明，不能继续向新 Chat 用户显示“游乐场”字样。
- 提示应支持说明模型来源、是否免费、可能产生的费用、适用场景和使用注意事项。
- 未配置专属提示时使用系统级新 Chat 默认提示，不能回退到游乐场文案。
- 提示配置必须按渠道 ID 与模型名称联合识别；相同模型名称存在于多个渠道时，可以配置不同内容。
- 渠道或模型被停用、删除后，历史提示配置可以保留但不再出现在普通用户可选列表中，避免重新启用后配置丢失。

#### 数据与接口边界

- 提示配置属于服务端数据，不能只保存在管理员浏览器本地。
- 普通用户获取可用渠道模型列表时，应同时获得对应的安全展示字段；不得因此暴露渠道密钥或上游敏感配置。
- 管理接口需要管理员权限，并记录新增、修改和删除提示配置的审计信息。
- 文案至少支持纯文本和换行；是否支持 Markdown、链接和富文本需要在实现阶段根据安全边界确定。

#### 验收标准

- 管理员可以在指定运维入口看到已接入的渠道模型组合。
- 管理员可以分别保存本地免费模型和付费模型的不同使用提示。
- 普通用户进入对应 Chat 后看到正确的标题和说明，且在发送消息前清晰可见。
- 切换到另一个渠道模型后，提示内容随渠道模型组合正确变化。
- 未配置的组合显示统一的新 Chat 默认提示，不显示原游乐场默认文案。
- 普通用户不能通过前端或接口修改提示配置。

#### 后续扩展方向（本阶段不实现）

- 针对渠道模型配置和展示知识库能力。
- 针对渠道模型配置 Skill。
- 针对渠道模型配置 MCP 服务与工具。
- 由运维人员统一控制上述能力的可见性、使用范围和风险提示。

实现状态：截至 2026-09-02，聊天提示管理第一阶段已完成：

- 已新增服务端 `chat_prompts` 配置表，按渠道 ID 与模型名称联合保存标题和说明。
- 已新增管理员查询、保存、恢复默认接口，并接入管理员权限和管理审计日志。
- 已在“系统设置 → 运维 → 渠道维护”中增加“聊天提示管理”，管理员可逐项编辑已接入的渠道模型组合。
- 新 Chat 获取渠道模型时会同时取得对应提示；未配置时返回统一的新 Chat 默认提示。
- 用户进入尚未发送消息的 Chat 页面时，会看到所选渠道模型的专属提示，不再显示游乐场默认文案。
- 已验证相同模型名称位于不同渠道时提示互不影响，并通过后端测试、前端类型检查、界面测试、代码检查和生产构建。
- 本阶段提示按纯文本展示；知识库、Skill、MCP 与更丰富的内容格式仍属于后续需求。

### 2026-10-13：自定义参数总开关与搜索入口隐藏

- Chat 参数设置增加“启用自定义参数”总开关，默认启用以兼容原有行为。
- 关闭时，流式与非流式请求省略 temperature、top_p、max_tokens、frequency_penalty、presence_penalty、seed；模型、消息、分组、流式模式和知识库/Skill 选择继续生效。
- 关闭后保留当前参数值与单项开关，参数控件禁用；重新开启恢复原配置，入口计数在关闭时显示 0。
- 状态在当前浏览器按登录用户、渠道 ID 和模型名称保存，返回列表、重新进入和刷新后仍生效；不跨浏览器同步。
- 隐藏 Chat 未实现的联网搜索按钮，保留相关代码及原始游乐场行为。

实现状态：已完成实现；三个回归测试、类型检查、相关文件 lint 和生产构建通过，等待用户界面验收。
